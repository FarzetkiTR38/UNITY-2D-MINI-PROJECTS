# ArrowSwarm ASO strategy

Prepared 13 November 2026. **Copy and test design are ready locally; no store listing is live or changed by this work.** Previous icon and Reels concepts were rejected. Their visual revision is deferred by the user's latest instruction; they are not selected test winners or approved production assets.

## Product position

The factual proposition is directional arrow puzzles in three modes: Shapes, Color Shift and Defense. “Classic” is not a fourth verified mode. The two authored catalogs contain 50 entries each. Catalog count and a native Shapes2 solution were verified in the earlier capture pass; a complete 100-level/device replay was not performed for this ASO document.

Lead with one understandable decision: read an arrow's route and choose the next move. Use Color Shift's stationary arrows and rotating outer frame as the second message; introduce Defense with an actual enemy/shot clip. Do not suggest all three modes have identical pacing. The expected audience is a test hypothesis: players interested in sequencing, visual shapes and clear, short-session decisions. No demographic conversion estimate is available.

## Listing structure

- Recommended draft names: **ArrowSwarm: Arrow Puzzle** (EN), **ArrowSwarm: Ok Bulmacası** (TR). Descriptive search intent accompanies the existing brand without a keyword list.
- Category proposal: Games / Puzzle. Choose only genuinely available, relevant Play Console tags after checking the final build and Console taxonomy. No tag changes were made.
- Use the short description to explain the three-mode decision, not repeat the title or promise health benefits. The full copy explains each mode, life cost and progress.
- First three screenshot slots: (1) an intact, readable Shapes board with one short premise, (2) an actual exit/motion moment from the same mode, (3) a genuine Color Shift frame/arrow color match. Defense can be fourth; campaign/theme/progress follow. This ordering is a hypothesis, not a measured winner.
- Keep real arrows large enough to read on a phone. Preserve genuine gameplay pixels; label editorial overlays. No mock rank, false victory, ad-free promise, Google Play badge or fabricated review.
- TR graphics need Turkish native HUD captures before release. The existing pilot has TR marketing text over EN gameplay and cannot be counted as a fully localized store set.

## Limits and policy control

Google's official setup reference specifies title 30, short 80 and full 4000 characters, including full-width characters. The validator counts Unicode code points plus UTF-16 units, includes long-copy newlines, rejects BOM/control-format characters and checks known unsupported claims. Both current texts fit. This is a mechanical/content lint, not a policy or store-review guarantee. [Setup](https://support.google.com/googleplay/android-developer/answer/9859152?hl=en).

Keep metadata factual and relevant. Avoid keyword stuffing, invented endorsements, rankings and unrelated promotional language. All translations must reflect the same release functionality. [Metadata policy](https://support.google.com/googleplay/android-developer/answer/9898842?hl=en), [listing practices](https://support.google.com/googleplay/android-developer/answer/13393723?hl=en).

## Keyword plan

KEYWORD_MAP.csv maps intents to placements, product evidence and validation. The words come from the verified game and official competitor-listing vocabulary; **search volume, competition difficulty, CPI and conversion are not measured**. Brand search and non-brand search must be tracked separately. Natural wording takes priority over repetition. “Tower defense” is a secondary hypothesis for the Defense page, not a label for every mode.

Use Play Console search/acquisition reports when available to learn which actual queries lead to useful installs. Do not claim that repeating “arrow puzzle” or changing a keyword guarantees ranking. No keyword-tool subscription was purchased.

## Three store experiment hypotheses

These are plans for a published/eligible listing, not tests already run. The Console's current metric choices include Unique user install clicks, Unique user open clicks and Unique user pre-registration clicks. Confirm the labels/definitions shown in the real account before analysis; do not substitute an older retained-installer metric. Test one asset family at a time. [Official experiments](https://support.google.com/googleplay/android-developer/answer/12053285?hl=en).

| ASO-03 | A concrete route/shape short description attracts a better-matched audience than a generic three-mode summary. | English localized experiment; change short description only. | Install target with Console's minimum detectable effect and confidence plan set before launch. | Monitor first5-level abandonment; do not trade deceptive clicks for poorer understanding. |

For each test, save start/end time, locale, traffic sources, variant hashes, chosen metric, MDE, confidence level and the Console sample/time estimate. Use one variant where traffic is low; do not split scarce traffic across many changes. A 50/50 split is an initial design proposal if the available UI permits it. Cover at least a full weekly cycle where practical and satisfy the sample requirement; “seven days passed” alone is not statistical evidence. If the Console says more data is needed, record inconclusive. Do not select a winner from daily peeking or a single install. Do not claim a lift before data exists. An organic before/after comparison is observational and must not be labelled a randomized A/B test.
